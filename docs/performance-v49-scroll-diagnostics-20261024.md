# Байна Ядайк v49 — диагностика вертикальной прокрутки, 24 октября 2026

## Цель и границы

Проверить причину ощущения «как 60 FPS» при вертикальной прокрутке на Android с экраном 120 Гц, сохранив Flutter, учебный контент, настройки, PDF и утверждённую глубину матовых 3D-карточек.

**База:** `codex/bayna-v48-android-skills-20261024` (наследует v47). **Работа:** `codex/bayna-v49-shadow-ab-diagnostic-20261024`. Никаких выводов о реальном 120 FPS без замеров на физическом телефоне.

## Факты из исходников

1. `lib/features/learning/situations_screen.dart`: диалоги используют ленивый `ListView.builder` с `cacheExtent: 180`. `course_screen.dart`: учебные разделы и уроки — `CustomScrollView` и `SliverList.builder`. Устранение этих списков или переписывание Flutter не обосновано.
2. `lib/ui/neumorphic_components.dart`: обычные светлые карточки имеют 2 слоя `BoxShadow`, акцентные — 3 (максимальный `blurRadius=35`). Это **возможный**, но пока не подтверждённый GPU bottleneck. Промышленный дизайн не меняется.
3. `lib/ui/fitted_study_artwork.dart`: `ImageFiltered.blur` заменяется на статическую маску только в сборке с `BAYNA_STATIC_SHADOW_ASSETS=true`. В обычной компиляции флаг по умолчанию выключен. Диагностический v47 APK собран с флагом включённым.
4. **Подтверждённый дефект корректности диагностики:** прежнее `blurSilhouette=false` исключало Gaussian blur, но *оставляло* отдельный `ColorFiltered`-силуэт и второй `Image`. Таким образом, подпись «Рисунки ВЫКЛ» не означала отсутствие теневой отрисовки. В v49 только для OFF возвращается `SizedBox.shrink()` вместо тени. Оригинальная картинка, обычный release, глубина карточки и ON полностью прежние.
5. `lib/ui/background_artwork_preloader.dart`: предварительная загрузка семи иллюстраций отложена до первого кадра и старается приостанавливаться при прокрутке. Полностью исключить GPU texture uploads из первого прохода можно только device trace.
6. `lib/core/performance_probe.dart`: `addTimingsCallback` считает p95 UI/raster за блоки 120 кадров, **не отбирая только кадры вертикального движения**. Поэтому HUD — ориентир для контролируемого A/B, а не независимая оценка delivered FPS. `View.display.refreshRate` также не является delivered FPS.
7. В проверенных `main.dart`, `app.dart`, AndroidManifest и Gradle **нет явного запрета 120 FPS или принудительных 60 Гц**. Не просмотрены все Android framework/устройственные policies: фактическую частоту нужно измерить.

## Доступная историческая device evidence (не результаты v49)

- На v43 в одном сценарии UI p95 ~4,6 мс, Raster p95 ~17,4 мс, >8,33 мс 162/165. Дубликаты кадров при переходах возможны, поэтому эти числа не независимы по экранам.
- v44 после диагностического сравнения сообщалось UI p95 ~3,7 мс и raster p95 ~12,2 мс на учебнике с тенями; при отключённых тенях в ином эксперименте 11,3–15,3 мс. Эти проходы **не равнозначны и не доказывают влияние именно карточек**.
- Для диалогов со всеми тенями OFF на v44 raster p95 ~3,9 мс (1/145 >8,33 мс), но сравнение с ON не было строго попарным.
- Версии v47/v48/v49 на одном физическом Android в воспроизводимой процедуре пока **не измерены**. Ни количество кадров быстрее 8,33 мс, ни p95 не является самостоятельным показателем реально показанных FPS.

## Исправление диагностического стенда v49

- `test/fitted_artwork_decode_test.dart`: отдельная проверка OFF требует ровно одно `Image` внутри `FittedStudyArtwork`, исходный предмет остаётся.
- `test/shadow_mode_isolation_test.dart`: в режиме «Рисунки ВЫКЛ» проверяется отсутствие второго рисунка.
- `lib/ui/fitted_study_artwork.dart`: только `blurSilhouette=false` не рисует тень, тогда как `true` по-прежнему рисует исходный 3D-силуэт (или подготовленную PNG-маску).
- Протокол Test-Driven Development: тест с новым инвариантом добавлен раньше изменения виджета. **RED не запущен локально — Flutter SDK в рабочем контейнере отсутствует.** Тесты и `flutter analyze` необходимо подтвердить через CI; не выдавать статическую проверку за успешный запуск.
- Для A/B предусмотрен отдельно устанавливаемый, development-signed `arm64-v8a` APK `com.example.arabic_academy.perf49`. Он не перезаписывает основную программу и её пользовательские данные.

## Протокол проверки на телефоне (обязательно перед оптимизацией GPU)

**Подготовка:** одно и то же устройство и режим 120 Гц в настройках Android; отключить энергосбережение; одинаковая тема, яркость, масштаб текста, температурное состояние; после прогрева изображений использовать один и тот же набор карточек и жестов. Строго фиксировать версию APK, ID пакета и меню GPU-режима.

**Два маршрута:** (A) Учебник → раздел → список уроков; (B) Разговорные ситуации → иллюстрированные диалоги. На каждом маршруте:
1. Прогреть список один раз и убрать телефон из состояния термального ограничения, не выходя из маршрута.
2. Сравнить **четыре** режима: `Карточки ВКЛ · Рисунки ВКЛ`, `Карточки ВЫКЛ · Рисунки ВКЛ`, `Карточки ВКЛ · Рисунки ВЫКЛ`, `Карточки ВЫКЛ · Рисунки ВЫКЛ`.
3. Каждую последовательность прогнать минимум 3 раза, меняя порядок условий при повторениях; переключение обнуляет накопленную выборку. Снимать HUD после 120 кадров *активного прокручивания*, без периода бездействия. В старом HUD 120 кадров могут содержать не только движение, поэтому для строгого анализа дополнительно использовать Flutter DevTools Performance / Android Perfetto.
4. Записать `display.refreshRate`, UI p50/p95, raster p50/p95, кадров >8,33 и >16,67 мс; по возможности Android FrameTimeline actual present/jank и 5 cold + 5 warm launch, 20 циклов навигации/память. **Не рассчитывать FPS как `1000/p95`.**

**Решение по результатам:**
- Если только отключение рисунков уменьшает raster p95 — изучить cache hit, fallback `ImageFiltered`, декод/загрузку PNG и bitmap upload, проверив совпадение внешнего вида OFF не как цель, а как диагностику.
- Если помогает отключение карточек — профилировать `BoxShadow`/offscreen слой и пробовать offscreen pre-render или raster cache **с точным восстановлением дизайна**.
- Если **ничто из четырёх режимов не улучшает** — не трогать тени, проверять Android refresh policy, нагрузку фона, UI rebuilds, PDF и frame pacing через Perfetto.
- Если UI p95 высокий — сперва найти вызывающий build/layout/state/IO, не оптимизировать GPU без доказательств.

## CI и безопасность

На предыдущей v47 `quality` и `android-arm64` завершились success, два `full-regressions` jobs были canceled — это не полный зелёный suite. В v49 проверить качество и артефакт отдельно. Ничего не объединять с production/main и не сообщать «120 FPS достигнуты» без одинаковых замеров на Xiaomi.

**Performance contract:** preserved. Production visual/code path preserved; only diagnostic shadow OFF contracts intentionally corrected. Rollback: исходная ветка v48 и предшествующий v47 commit остаются нетронутыми.
